# Data Model: Remove Copy to Today Functionality

**Feature**: 012-remove-copy-today  
**Date**: October 25, 2025  
**Status**: Complete

## Overview

This document describes the data model changes for removing the Copy to Today functionality. The primary change is soft-deprecating the `templateSource` field in the Entry model while preserving existing data for audit purposes.

---

## Affected Entities

### Entry (Modified)

**Description**: Represents a single fasting entry for a user on a specific date. The `templateSource` field is being deprecated - it will no longer be populated for new entries but existing values are preserved.

#### Schema

```javascript
{
  // Core fields (unchanged)
  _id: ObjectId,                    // MongoDB-generated unique identifier
  userId: ObjectId,                 // Reference to User who owns this entry
  date: Date,                       // Entry date (stored at noon UTC to avoid timezone issues)
  
  // Meal timing (unchanged)
  firstMealTime: String,            // Format: "HH:mm" (e.g., "13:30")
  lastMealTime: String,             // Format: "HH:mm" (e.g., "21:00")
  
  // Optional health metrics (unchanged)
  morningWeight: Number,            // Weight in kg or lbs (based on user settings)
  sleepHours: Number,               // Hours of sleep (0-24)
  energyLevel: String,              // Enum: "Low Energy", "Medium Energy", "High Energy"
  hungerLevel: String,              // Enum: "Not Hungry", "Slightly Hungry", "Very Hungry"
  wellBeing: String,                // Enum: "Poor", "Fair", "Good"
  foodIntakeNotes: String,          // Free-text notes (max 2000 chars)
  
  // Audit trail (DEPRECATED)
  templateSource: ObjectId | null,  // ⚠️ DEPRECATED - no longer populated for new entries
                                    // Historically: Reference to entry this was copied from
                                    // Preserved for audit trail only
  
  // Timestamps (unchanged)
  createdAt: Date,                  // Auto-generated by Mongoose
  updatedAt: Date                   // Auto-generated by Mongoose
}
```

#### Changes

| Field | Change Type | Description |
|-------|-------------|-------------|
| `templateSource` | **Deprecated** | No longer populated for new entries. Existing values preserved for audit trail. Will be null/undefined for all entries created after this change. |

#### Indexes (No Changes)

```javascript
// Existing indexes remain unchanged
{userId: 1, date: -1}  // Primary query pattern: user's entries by date
{userId: 1}            // Find all entries for a user
```

**Note**: `templateSource` was never indexed and doesn't need to be. Optional fields perform fine without indexes when rarely queried.

#### Validation Rules (Modified)

**Previous Validation** (being removed):
```javascript
templateSource: Joi.string()
  .regex(/^[0-9a-fA-F]{24}$/)
  .optional()
  .description('ObjectId of source entry if copied from another entry')
```

**New Validation** (removed entirely):
- Field removed from Joi schema
- API will ignore templateSource if provided in requests (stripUnknown behavior)
- No validation errors for legacy entries with templateSource values

#### Business Rules

**Previous Rules** (no longer applicable):
- ~~"Copy to Today" feature populated templateSource with source entry's \_id~~
- ~~System prevented copying if target date already had an entry~~
- ~~Only firstMealTime and lastMealTime were copied (health metrics left null)~~

**Current Rules**:
- New entries created through any method will have templateSource = null
- Existing entries with templateSource values are displayed/queried normally
- No business logic uses templateSource field
- Field presence does not affect calculations, validations, or display

#### Migration Strategy

**No Migration Required**

- **Existing Data**: All entries with templateSource values remain unchanged
- **New Data**: All new entries will have templateSource = null or undefined
- **Schema**: Field remains in schema marked as deprecated (JSDoc comment)
- **Queries**: No query changes needed (field is optional, gracefully handled)

**Rationale**: Additive schema evolution - preserve history, stop populating going forward.

---

## Entity Relationships (No Changes)

```
User (1) ────< (many) Entry
```

**Notes**:
- `Entry.userId` → `User._id` (existing relationship, unchanged)
- `Entry.templateSource` → `Entry._id` (deprecated, no longer used in queries or business logic)

---

## Data Integrity

### Constraints (No Changes)

- `userId` required (cannot create entry without user)
- `date` required (cannot create entry without date)
- `firstMealTime` required (cannot create entry without start time)
- `lastMealTime` required (cannot create entry without end time)
- Unique constraint: One entry per user per date (enforced at API level)

### Audit Trail (Preserved)

- Existing `templateSource` values preserved for historical audit purposes
- `createdAt` / `updatedAt` timestamps unchanged
- No data loss from this feature removal

---

## Performance Considerations

### Query Performance (Improved)

**Before Removal**:
- Copy functionality queried: "Does today's entry exist?" + "Create new entry with templateSource"
- Extra validation: Check templateSource is valid ObjectId

**After Removal**:
- One fewer API call (no copy requests)
- Simpler validation (one less field to validate)

**Impact**: Marginal improvement (< 50ms per avoided copy operation)

### Storage Impact (Negligible)

- `templateSource` field: ~12 bytes per entry (ObjectId)
- Existing entries: Kept (no cleanup needed)
- New entries: One less optional field populated
- **Estimated savings**: < 1KB per 100 new entries (negligible)

---

## Backward Compatibility

### API Compatibility

- **POST /api/entries with templateSource**: Field ignored (not rejected)
- **GET /api/entries**: Returns entries with or without templateSource (optional field)
- **Legacy clients**: Continue to work (field is optional)

### Data Compatibility

- **Old entries**: Displayed normally (templateSource value irrelevant to UI)
- **New entries**: Created normally (templateSource not populated)
- **Mixed data**: System handles both gracefully

---

## Security & Privacy

### No Security Impact

- Removing copy functionality eliminates a code path (reduces attack surface marginally)
- templateSource never contained PII (just entry IDs)
- Audit trail preservation maintains compliance

### Privacy Compliance

- Historical templateSource values don't violate GDPR (legitimate audit interest)
- User can still delete entries (cascade deletes templateSource references naturally)
